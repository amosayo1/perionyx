================================================================================
  PERIONYX — Enterprise Treasury Operating System
  Full Project Description
================================================================================

1.  OVERVIEW
    ----------------------------------------------------------------------------
    A multi-tenant, double-entry treasury and financial operations platform.
    Each tenant is a COMPANY with isolated wallets, transactions, users, roles,
    policies, and bank connections. Built for teams that need coordinated
    approval workflows, policy enforcement, bank integration, and audit trails.

4.  TENANCY & SECURITY
    ----------------------------------------------------------------------------
    Tenant isolation:   Every API route passes through requireTenantContext()
                        which extracts { userId, companyId, role } from the JWT
                        session. All database queries scoped by companyId.

    Registration:       Invite-only after the first company exists.
                        First user registers without invite (no companies exist),
                        then creates their company as OWNER.

    Company creation:   Only users with NO existing memberships can create
                        a company. After one company exists, no more can be
                        created (everyone is invited in, gets a membership).

    License:            LICENSE_COMPANY_ID env var — hard gate at
                        requireTenantContext(). If set, only that company ID
                        passes. Optional License table with HMAC-SHA256 signed
                        keys for programmatic management.

    Authentication:     Auth.js with JWT, HTTP-only cookies, CSRF origin
                        validation, rate limiting (Redis + in-memory fallback).

8.  KEY BUSINESS FLOWS
    ----------------------------------------------------------------------------
    A. WALLET CREDIT / TRANSFER

       1) Validate wallet exists, balance sufficient (for debits)
       2) Evaluate policies — if BLOCK, reject immediately
       3) Evaluate approval rules — if thresholds met:
          a) Store ledger lines in transaction metadata
          b) Create PENDING_APPROVAL records
          c) Set status to PENDING_APPROVAL
          d) Notify all eligible approvers (via NotificationService +
             webhook queue)
          e) Return early
       4) If no approval needed:
          a) Create LedgerEntry records
          b) Update wallet balance (optimistic lock via version field)
          c) Mark transaction COMPLETED
       5) On approval (route): approve step → check if fully approved →
          if yes, replay stored ledger lines (create entries, update
          balances, mark COMPLETED)

    B. INVITATION FLOW

       1) Admin sends invite via /admin/users UI → select email + role
       2) Service creates Invitation record with crypto token
       3) Sends HTML email: BASE_URL/invite/{token} (7-day expiry)
       4) Recipient clicks link:
          - If not signed in: redirect to /sign-up?token=...
          - If signed in: show "Accept & join" button
       5) Registration includes inviteToken → server validates email match
          → auto-accepts → creates membership with role → redirects to
          dashboard

    C. FIRST-TIME SETUP

       1) Deploy with zero companies in DB
       2) Register via API (no invite needed — detect 0 companies)
       3) Create company via POST /api/v1/companies → become OWNER
       4) Now company exists → all future registrations require invite
       5) Use /admin/users to invite team members

    D. LICENSE ENFORCEMENT

       1) LICENSE_COMPANY_ID env var checked in requireTenantContext()
          — synchronous, per-request
       2) License table with signed keys (HMAC-SHA256) for programmatic
          management via admin API
       3) 60s in-memory TTL cache to reduce DB hits
       4) Seat validation: check CompanyMembership count against
          license.seats at invite time


9.  TRANSACTION STATES
    ----------------------------------------------------------------------------
    PENDING           Created, not yet processed
    PROCESSING        Ledger entries being applied
    COMPLETED         Successfully processed
    FAILED            Processing failed
    REVERSED          Reversed after completion
    CANCELLED         Cancelled before processing
    PENDING_APPROVAL  Awaiting approval workflow


10. ROLES & PERMISSIONS
    ----------------------------------------------------------------------------
    OWNER............. Full access, can manage everything
    ADMIN............. Administrative access (users, roles, settings)
    TREASURER......... Can initiate and approve transactions
    MEMBER............ Basic access (view, limited actions)
    VIEWER............ Read-only access

    Permissions are granular strings (e.g., "transactions.transfer",
    "approvals.approve", "admin.manage_users") assigned to roles via
    RolePermission table.
