# Engineering Decision Packet — Phase 22.3 — Decision Workspace

## 1. Overview

### Phase Purpose
Transform the Invoice Workspace (`/procurement/invoices/[invoiceId]`) from a details page into the canonical Perionyx **Decision Workspace** — the evidence-first, auditable financial decision surface.

### First Principle
> A financial system earns trust by showing **why** a decision exists, not just what the decision is.

### Scope
- Deliverable 1: `DECISION_WORKSPACE_AUDIT.md` — baseline (verdict: "details page, not a decision surface"; compliance ~35%; 15 findings SEV-1…15).
- Deliverable 2: `DECISION_WORKSPACE_REDESIGN_SPEC.md` — 3-zone layout, data model, deterministic recommendation, timeline, action matrix, keyboard-first, EDL compliance.
- Implementation: `src/modules/decision-workspace/` (6 files) + `src/components/decision-workspace/` (9 files) + rewired `src/app/(shell)/procurement/invoices/[invoiceId]/page.tsx`.
- Deliverable 3: `DECISION_WORKSPACE_VALIDATION.md` (this phase's evidence; compliance ~90%).
- **No new API surface.** Actions reuse existing `/api/v1/ap/invoices/[id]/{approve,reject,escalate,block,dispute,void}`.
- **No regressions** to Phase 22.2 Dashboard v2 or existing AP endpoints.

### Companion Documents

## 2. Key Decisions

### D-01: Deterministic recommendation — never a fabricated scalar
The audit found a stub AI service that fabricated `confidence: 0.15` (SEV-2) — a number with no measured basis. The workspace recommendation is **rule-based and categorical**:

1. **REJECT** if duplicate confidence ≥ 0.8 (high band)
2. **REVIEW** if any unresolved exception exists
3. **REVIEW** if no match / not `FULL_MATCH` / match confidence band < 0.6
4. **APPROVE** on a clean full match
5. **NO-SIGNAL** on terminal/informational statuses

Confidence is always one of `high|medium|low|none` with a mandatory `confidenceBasis` naming the measured data. `recommendation.ai` is reserved as `null` for the future Decision Intelligence platform. Every decision is unit-tested.

**Rationale:** CFOs need to re-derive the recommendation by hand from the evidence. A scalar without a basis is untrustworthy; a band + basis is auditable. (DI-R2, DI-P4)

### D-02: One format module, server-side
All money/date/number formatting lives in `src/modules/decision-workspace/format.ts` and runs **server-side**; every `EvidenceItem.value` is a pre-formatted string. No client-side `Intl` money formatting (F-08).

**Alternative considered:** a client `formatted` bag (spec §5.5 draft). Rejected — two formatting paths invite drift, and the spec itself demands server-formatted values.

### D-03: No new API surface
Actions map to existing AP endpoints only. `request-info` and `assign` were dropped from `AvailableAction` because no endpoint exists. Adding endpoints would require permission registry + tests + docs for marginal value; the EPS approval flow (Phase 27.0B) will own request-info.

### D-04: Mirror status guards, don't invent them
`buildActions()` in the workspace service mirrors the guards in `src/server/procurement/application/invoice-service.ts`:
- approve/escalate: `MATCHED` / `PENDING_APPROVAL`
- reject: `MATCHED` / `PENDING_APPROVAL` / `APPROVED`
- block/void: `CAPTURED` / `VALIDATED`
- dispute: `CAPTURED` / `VALIDATED` / `MATCHED`

If the domain guards change, the workspace must be updated — a single comment in the service marks the coupling.

### D-05: Client components deep-import types + format only
The build failed on the H-01 hazard: `workspace-timeline.tsx` imported the module **barrel**, which re-exports the Prisma-backed `decisionWorkspaceService`, pulling `pg` into the client bundle (Turbopack error on Node `dns`). Client components now import `@/modules/decision-workspace/types` and `.../format` directly; only the server page imports the barrel. This is now a documented platform rule (H-01) — barrel = server-only.

### D-06: PO/GRN loaded directly from Prisma
The AP repository layer has no PO/GRN repositories. `decisionWorkspaceService` loads `ProcurementPOReference`/`ProcurementGRNReference` via Prisma directly (`include: { lineItems: true }`, scoped by `companyId`), using `toNumber`/`toIso` helpers. Documented residual gap; a repository adapter can replace this without touching the surface contract.

### D-07: Evidence absence is disclosed, never silent
Every absence produces an explicit `negative`/`pending` item (`po.none`, `grn.none`, `vendor.missing`, `match.none`, `tx.none`, `similar.none`, `comm.none`, `docs.none`) with a why-it-matters explanation. Confidence never pretends to be high where data is missing.

### D-08: Keyboard-first, guarded
`?` opens the legend; `a` approve · `r` reject · `x` escalate (P1); `b` block · `v` void · `d` dispute · `k`/`j` navigate evidence · `t` jump to timeline (P2–3). `isTypingTarget()` guard prevents shortcuts while typing in inputs/textareas.

## 3. Alternatives Considered

| Alternative | Decision | Why rejected |
|---|---|---|
| Wire the stub AI service for confidence | Rejected (D-01) | It fabricated scalars; violates DI rules |
| New API routes for actions | Rejected (D-03) | Security review burden + no permission need |
| Client-side `formatted` bag | Rejected (D-02) | Two formatting paths = drift |
| Keep barrel imports in client components | Rejected (D-05) | Build fails on `pg` in client bundle |
| Reuse `invoice-workspace/` components in place | Rejected | Deprecated; left untouched as the audit baseline |

## 4. Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Status-guard drift between workspace and invoice-service | Medium | Single mirrored `buildActions()` + comment; add a guard-mirroring test if the AP flows change |
| Demo data empty (0 AP invoices for Demo Company) | Medium | Not seeded per user decision; seed repair is tracked separately |
| PO/GRN direct-Prisma query bypasses repo layer | Low | Scoped by `companyId`; documented as adapter-able |
| `ai: null` until DI ships | Low | Evidence package is the DI contract; no fake output in the interim |
