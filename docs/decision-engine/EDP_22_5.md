# Engineering Decision Packet — Phase 22.5 — Decision Intelligence Engine

## 1. Overview

### Phase Purpose
Deliver the canonical **Decision Intelligence Engine** — the deterministic enterprise reasoning layer behind every future financial workflow. Phase 22.3 built the Decision Workspace surface with a deterministic *recommendation heuristic* (`recommendation.ts`, band + basis). Phase 22.4 built the Evidence Engine and its package. Phase 22.5 generalizes the recommendation logic into a **generic, registry-extensible reasoning engine** that consumes the Phase 22.4 Evidence Package and produces an auditable Decision artifact — and wires it into the workspace additively.

### First Principle
> The engine explains the decision but never makes it.

### Scope
- `src/modules/decision-engine/` — 14 files (~1,700 lines): canonical types, 4 engines (rule, policy, risk, confidence), reasoning graph, explanations, recommendation ladder, lifecycle, registry, facade, Evidence→Decision adapter, and the `ap.invoice` reference decision type.
- Additive workspace integration: `DecisionWorkspaceData.decision`, `assembleEvidencePackage`/`projectEvidenceGroups` exports, `buildDecisionFacts()`.
- `test/decision-engine.test.ts` — 40 unit tests.
- No new API surface, no new dependencies, no UI changes, no writes.

### Companion Documents

## 2. Key Decisions

### D-01: The engine is deterministic enterprise reasoning — explicitly not AI
The engine runs declarative rules, policies, risk factors, and confidence weights over normalized evidence. It never uses probabilities or an LLM. Confidence is a categorical band with a measured basis; recommendations are one of six fixed states.

**Rationale:** CFOs must be able to re-derive any recommendation by hand from the evidence. Probability is un-auditable; a deterministic graph is reproducible and regulator-safe (DI-R2, DI-P4, DI-P5, Measured-Confidence Doctrine). A future LLM capability may only *summarize* the reasoning graph — it may never produce the decision (PP-102).

### D-02: Four engines, one shared condition DSL
Rules, policies, risk factors, and confidence factors all evaluate the **same** declarative `RuleCondition` union through the single `matchCondition()` evaluator. `anyConditions` (OR across groups) is honored uniformly — including risk factors.

**Rationale:** One DSL means one mental model, one test surface, and no drift between engines (PP-105 — no free-text rules). Evidence discovered how to express absence: `missing` conditions (scoped blocking/advisory) + `metadata.stale`.

### D-03: New module `decision-engine`, legacy `decision-intelligence` untouched
The Phase 7 `decision-intelligence` module (scoring engine, briefing, jobs) is live and consumed by six modules. Phase 22.5 ships a **new** canonical module instead of overwriting the legacy one.

**Rationale:** Overwriting would break automation-studio, command-center, copilot, dashboard, and the workflow decision step. The legacy module is a documented migration candidate; its consumers remain stable.

### D-04: Additive workspace integration — one evidence package, two projections
The workspace already assembles the evidence package for its 14-group layout. Phase 22.5 feeds the **same** package into `fromEvidencePackage()` → `evaluateDecision()`. `DecisionWorkspaceData` gains a single additive `decision` field.

**Rationale:** Zero re-fetching, zero divergent evidence, zero UI change. The Phase 22.3 `summary.recommendation` remains the UI contract; the engine's Decision is the audit-grade superset. (D-05 of 22.3's `ai: null` reservation is now fulfilled — `ai` is reserved for a future LLM summarizer, not the decision.)

### D-05: Confidence weights normalized over ALL factors
`score = (Σ positives − Σ negatives) / Σ all weights`. Missing positive factors genuinely lower confidence instead of only raising it; a clean package scores 0.80 → `high`, and any degradation (partial match, open exception, first-time supplier, flagged duplicate) drops to `moderate`.

**Rationale:** Prevents the "everything is high" failure mode where missing evidence silently inflates trust. Bands remain categorical — the score is internal only and never exposed.

### D-06: Risk severity tuned so priority tiers mean what they say
Two defects surfaced during validation: `risk.no-match` at `high` escalated every partial match, and `risk.overdue` at `medium` sent overdue invoices to `needs-review`. Both were downgraded (`medium`, `low`).

**Rationale:** An unverified match is a review item, not a CEO escalation; an overdue invoice must not be held in review — that worsens the delay. The ladder (escalate ≥ high, review ≥ medium) only works when severities encode their intent.

### D-07: `conf.audit-missing` dropped — the DSL cannot express "NOT exists"
The original factor asserted `audit.*` status `none`, which is not a valid `EvidenceStatus`, and required a negative-existence evidence condition the DSL lacks. Since absent audit simply misses the `conf.audit-present` positive factor, the negative factor was removed — absence lowers confidence exactly as the doctrine intends.

**Rationale:** Never fake an absence signal; the DSL encodes presence, and missing positives handle absence. Adding a NOT-exists operator is a deliberate future extension, not a hack.

### D-08: Determinism hash includes factor definitions, excludes time
`determinismHash` = sha256 over `{ evidence (now stripped), rules, policies, riskFactors, confidenceFactors, version }`. `now` is excluded so re-evaluations and tests are time-stable; factor definitions are included so a rule change invalidates prior hashes — the audit trail cannot silently masquerade as a new evaluation.

**Rationale:** Auditors must be able to prove "this recommendation came from this evidence under these rules at this engine version."

## 3. Alternatives Considered

| Alternative | Decision | Why rejected |
|---|---|---|
| Extend the Phase 22.3 workspace heuristic instead of a generic engine | Rejected (D-03) | Each workflow would fork its own recommendation logic — the "4th duplicate currency" problem at the recommendation layer |
| Overwrite the legacy `decision-intelligence` module | Rejected (D-03) | Six live consumers would break; migration belongs in a dedicated phase |
| Confidence = scalar probability (e.g. 0.85) | Rejected (D-01) | Unauditable, violates DI-R2 / Measured-Confidence Doctrine |
| Confidence = sum of positives only | Rejected (D-05) | Missing evidence would not lower confidence |
| LLM summarizes the reasoning graph now | Deferred | No provider contract yet; deterministic core ships first, LLM is a consumer |
| Add a NOT-exists evidence operator for audit-missing | Rejected (D-07) | Not needed for a clean factor set; absence is already handled by missing positives |

## 4. Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Legacy `decision-intelligence` drift vs new engine | Medium | Module boundary documented; consumers unchanged; migration tracked as future phase |
| Rule/fact-key drift between workspace `buildDecisionFacts()` and `ap.invoice` conditions | Medium | `AP_DECISION_FACT_KEYS` is the documented contract; rules reference only contract keys |
| Confidence weights drift from intent | Low | Bands are unit-tested (clean → high, degraded → moderate, blocking → insufficient) |
| Determinism broken by an unordered config | Low | `determinismHash` serializes canonical configs; add a sort-normalization step if a config ever orders dynamically |
| Staleness boundary owned by evidence engine | Low | Documented; `metadata.freshness.stale` is the single input |

## 6. Security Checklist (AGENTS.md 10 questions)

| # | Question | Answer |
|---|---|---|
| 1 | Exposes sensitive financial data? | **No** — the engine reads `DecisionEvidence` in memory; it never reads or writes persistence. The workspace payload already carried financial data under existing permission checks |
| 2 | New permission required? | **No** — no new mutations; the workspace page's existing access controls apply unchanged |
| 3 | Cross-tenant access? | **No** — `tenantId` is required on input; the engine holds no cross-tenant state; the workspace service already scopes every query by `companyId` |
| 4 | Audit logging needed? | **Yes** — the Decision artifact carries its own audited lifecycle transitions + determinism hash (the engine's audit surface); no IAM/audit-table writes added because the engine is stateless by design |
| 5 | Encryption required? | **No** — no new PII/financial data at rest; `facts` are in-memory numbers/booleans |
| 6 | Reversible? | **N/A** — the engine performs no mutations |
| 7 | Privilege escalation? | **No** — no endpoints added; no permission checks bypassed |
| 8 | New secrets? | **No** |
| 9 | Rate limiting? | **No** — no public endpoint added; evaluation runs inside the existing authenticated workspace route |
| 10 | Security architecture compliance? | **Yes** — tenant isolation, no new surface, deterministic auditable output, no untrusted input executed (conditions are declarative, not code) |
