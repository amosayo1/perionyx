# Engineering Decision Packet — Phase 19.1

**Phase**: 19.1 — Financial Foundation Implementation
**Status**: Implementation Complete
**Date**: 2026-07-21
**Predecessor**: Phase 19.0 — Financial Core Consolidation (Inventory)

---

## Mission

Strengthen the financial foundation by eliminating confirmed integrity risks identified in Phase 19.0 inventory. Every monetary value that flows through the application layer must maintain precision from database to display. No phantom rounding errors, no allocation drift, no silent precision loss.

---

## Validated Findings (Phase 19.0 Inventory)

| Finding | Classification | Severity |
|---------|---------------|----------|
| 4 Prisma Float fields storing monetary values | **CONFIRMED** | P0 — storage precision loss |
| 98 `Number()` conversions across financial paths | 84 UNSAFE (arithmetic), 14 SAFE (display) | P1 — calculation precision loss |
| GL allocation engine has no residual handling | **CONFIRMED** | P1 — allocation drift |
| Cash application accumulates in native `number` | **CONFIRMED** | P1 — phantom unallocated amounts |
| Tax integration uses `Math.round()` | **CONFIRMED** | P1 — asymmetric rounding bias |
| Morning briefing aggregates via `reduce()` sum | **CONFIRMED** | P1 — precision loss on large aggregates |

## Scope

### P0 — Float → Decimal Migration

Migrate all 4 Prisma Float fields storing monetary values to `Decimal(20,4)`:

| Model | Field | Before | After |
|-------|-------|--------|-------|
| `MorningBriefing` | `pendingApprovalAmount` | `Float` | `Decimal @db.Decimal(20,4)` |
| `MorningBriefing` | `cashPosition` | `Float` | `Decimal @db.Decimal(20,4)` |
| `MorningBriefing` | `cashChange` | `Float` | `Decimal @db.Decimal(20,4)` |
| `ApprovalMatrixRule` | `thresholdValue` | `Float` | `Decimal @db.Decimal(20,4)` |

### P1 — Unsafe Arithmetic Remediation

| Area | Fix |
|------|-----|
| GL Allocation Engine | Added residual handling (last target gets remainder), uses `financialRound` |
| Cash Application | Accumulation now uses `financialRound(2)` at each step |
| Tax Integration | All arithmetic uses `financialRound` instead of `Math.round` |
| Morning Briefing Computation | Replaced native `reduce()` sum with `sumDecimals()`, replaced `Number()` aggregate with `toDecimal().toNumber()` |

### P2 — Canonical Financial Helpers

Created `src/lib/financial-precision.ts` with 13 exported functions:

| Function | Purpose |
|----------|---------|
| `financialRound(value, decimals?)` | Banker's rounding via `Intl.NumberFormat` |
| `toDecimal(value)` | Safe conversion from `number \| string \| Decimal` to `Decimal` |
| `sumDecimals(...values)` | Safe aggregation of Decimal values |
| `multiplyDecimals(a, b)` | Safe Decimal multiplication |
| `divideDecimals(a, b, precision?)` | Safe Decimal division with configurable precision |
| `allocateAmount(total, allocations)` | Percentage-based allocation with residual handling |
| `calculateTax(amount, rate, rounding?)` | Decimal-safe tax calculation |
| `calculateWithholding(amount, rate, rounding?)` | Decimal-safe withholding calculation |
| `toDisplayNumber(value, decimals?)` | Safe conversion for display formatting |
| `formatDecimalCurrency(value, currency, options?)` | Currency formatting with Intl.NumberFormat |
| `formatDecimalCompact(value, currency?)` | Abbreviated currency formatting (K/M/B) |
| `decimalEquals(a, b, tolerance?)` | Comparison with configurable tolerance |
| `isValidMonetaryAmount(value)` | Validation helper |

## Changes Made

### Prisma Schema

- **4 Float fields → `Decimal @db.Decimal(20,4)`**: `MorningBriefing.pendingApprovalAmount`, `MorningBriefing.cashPosition`, `MorningBriefing.cashChange`, `ApprovalMatrixRule.thresholdValue`

### Migration

- **`20260721000000_financial_integrity_float_to_decimal`**: `ALTER COLUMN` for 4 fields converting `DOUBLE PRECISION` → `DECIMAL(20,4)`

### MorningBriefing Service

- Computation now uses `sumDecimals()` / `toDecimal()` instead of native `reduce()` sum
- Writes values as `String()` for Prisma Decimal compatibility

### ApprovalMatrixRule

- `thresholdValue` now passes through `Number(String())` for evaluator compatibility after Decimal migration

### GL Allocation Engine

- Added residual handling: last target receives `total - sum(previous allocations)`
- All intermediate amounts rounded with `financialRound(2)`
- Prevents allocation drift where `sum(entries) ≠ total`

### Cash Application

- Raw accumulation replaced with `financialRound(2)` at each step
- Prevents phantom unallocated amounts from floating-point drift

### Tax Integration

- All `Math.round(n * 100) / 100` replaced with `financialRound(n, 2)`
- Uses banker's rounding (round-half-to-even) for consistency

### Financial Precision Helpers

- New file: `src/lib/financial-precision.ts`
- 13 exported functions covering rounding, conversion, aggregation, allocation, tax, formatting, comparison, validation
- All functions accept `number | string | Prisma.Decimal` inputs
- Zero dependencies beyond `Prisma.Decimal` and `Intl.NumberFormat`

## Risk Assessment

**Overall Risk: LOW**

| Risk | Severity | Mitigation |
|------|----------|------------|
| Prisma Decimal compatibility | Low | Prisma accepts `number | string` for Decimal fields — no consumer changes required |
| Evaluation logic | Low | `thresholdValue` passes through `Number(String())` for evaluator compatibility |
| Morning briefing reads | Low | Service layer converts to `toDecimal().toNumber()` for backward-compatible API responses |
| Display formatting | None | All display formatting unchanged — `formatMoney()` accepts `number` |
| Existing test suite | None | 443 tests pass — Decimal fields are not directly tested in UI layer |
