# EDP 24.0 — Enterprise Foundation Implementation

## Engineering Decision Packet

**Phase**: 24.0
**Date**: 2026-07-22
**Author**: AI Engineering Agent

## Decision 1: Singleton Registries for All Platforms

**Decision**: All 5 foundation platforms use singleton pattern (getInstance()).

**Alternatives**:
- A) Module-level singletons
- B) Dependency injection container
- C) Global variables

**Rationale**: Singletons guarantee one instance per process, which is essential for shared state (circuit breaker state, capability health, config cache). DI containers add complexity without benefit at this stage. Global variables are untestable.

**Trade-off**: Testing requires resetting singletons. Mitigated by `reset()` methods on all registries.

## Decision 2: Token Bucket Rate Limiting

**Decision**: Use token bucket algorithm for rate limiting (not sliding window or fixed window).

**Alternatives**:
- A) Sliding window counter
- B) Fixed window
- C) Leaky bucket

**Rationale**: Token bucket allows controlled bursts (essential for batch operations) while maintaining average RPM. Leaky bucket smooths too aggressively for financial API patterns.

## Decision 3: Exponential Backoff with Jitter

**Decision**: Retry with exponential backoff + random jitter (factor 0.2).

**Alternatives**:
- A) Linear backoff
- B) Fixed delay
- C) No jitter

**Rationale**: Exponential backoff prevents overwhelming a recovering provider. Jitter prevents thundering herd when multiple clients retry simultaneously.

## Decision 4: Pluggable Secret Providers

**Decision**: Abstract ISecretProvider interface with Environment as default.

**Alternatives**:
- A) Direct env var access
- B) HashiCorp Vault only
- C) File-based secrets

**Rationale**: Environment provider works for dev/testing. Production will need Vault/AWS/Azure. The abstraction allows swapping without consumer changes.

## Decision 5: Capability-Based Provider Discovery

**Decision**: Providers declare capabilities (category + subcategory), consumers query by capability.

**Alternatives**:
- A) Hardcoded provider mappings
- B) Service registry (Consul-style)
- C) DNS-based discovery

**Rationale**: Capability-based discovery enables dynamic provider swapping, load balancing, and failover without consumer code changes. Matches the Provider Driver Model (Constitution).

## Decision 6: Abstract ProviderDriver Base

**Decision**: All providers inherit from ProviderDriver which implements retry, circuit breaker, rate limiting, metrics.

**Alternatives**:
- A) Middleware/wrapper pattern
- B) Decorator pattern
- C) Each provider implements its own

**Rationale**: Base class guarantees consistent behavior across all providers. Middleware adds indirection. Each provider implementing its own leads to inconsistency (the problem we're solving).

## Decision 7: 11-Level Classification System

**Decision**: 11 classification levels from PUBLIC (0) to TOP_SECRET (9), with PCI at 7.

**Alternatives**:
- A) 5-level system (Public/Internal/Confidential/Restricted/Secret)
- B) NIST 4-level (Low/Moderate/High/Critical)
- C) Custom per-domain levels

**Rationale**: Enterprise financial platforms need granularity between PII (5), PHI (6), PCI (7), Secret (8), and Top Secret (9). A 5-level system can't distinguish between these.

## Decision 8: Feature Flags with Percentage Rollout

**Decision**: Feature flags support boolean + percentage-based rollout.

**Alternatives**:
- A) Boolean only
- B) Boolean + user segment targeting
- C) Full LaunchDarkly-style feature flags

**Rationale**: Percentage rollout is sufficient for safe progressive delivery. Full targeting adds complexity without current need. Can be extended later.

## Decision 9: Hierarchical Config Resolution

**Decision**: Config resolves Tenant > Environment > Global.

**Alternatives**:
- A) Flat config (no hierarchy)
- B) Environment > Global (no tenant)
- C) Tenant > Global (no environment)

**Rationale**: Enterprise SaaS requires per-tenant overrides (e.g., different SMTP servers). Environment layer enables dev/staging/prod separation. Both layers are needed.

## Decision 10: In-Memory Capability Registry

**Decision**: CapabilityRegistry is in-memory (per-process), not persisted.

**Alternatives**:
- A) Database-backed
- B) Redis-backed
- C) In-memory with event sourcing

**Rationale**: Capabilities are runtime declarations, not persistent state. Providers register on startup. If the process restarts, providers re-register. Database persistence adds unnecessary latency for discovery.
