# Engineering Decision Packet — Phase 22.4 — Evidence Engine

## 1. Overview

### Phase Purpose
Build the canonical **Evidence Engine** — a generic, domain-agnostic evidence-assembly engine in `src/modules/evidence/` that becomes the single source of truth for financial evidence. Modules stop hand-composing evidence; they request an `EvidencePackage` and receive canonical sections, measured confidence, explicit absence, and a decision-readiness verdict.

### First Principle
> Every financial decision must be re-derivable by hand from the evidence that produced it.

### Scope
- **Engine core** (5 files): `types.ts`, `registry.ts`, `resolver.ts`, `assembler.ts` (incl. `assembleEvidenceFor()` facade), `index.ts`.
- **Provider groundwork** (2 files): `providers/ap/helpers.ts`, `providers/ap/loaders.ts` (14 `EVIDENCE_LOAD_KEYS`, seeded + repository fallback loaders).
- **11 AP reference providers** + `register.ts` + `index.ts` — thin adapters over the canonical AP repositories, zero domain-logic duplication.
- **Workspace rewiring**: `decision-workspace/evidence.ts` becomes an async engine adapter; `workspace-service.ts` awaits it.
- **Tests**: `test/evidence-engine.test.ts` (11 new) + `test/decision-workspace.test.ts` (14, kept green via async migration).
- **No AI, no persistence, no UI change, no new API surface.**

### Companion Documents
`ARCHITECTURE.md` · `EVIDENCE_PACKAGE.md` · `VALIDATION.md` · `docs/decision-workspace/EDP_22_3.md` (convention source) · Product System 06 (Decision Intelligence) · Phase 23.0 Constitution (Laws 3, 6, 11, 12, 15).

## 2. Key Decisions

### D-01: Evidence → reasoning → recommendation → action, never inverted
The engine produces **evidence only**. It never computes a recommendation; it computes `decisionReady` (a boolean: are any blocking requireds unfilled?) and `missing`. The Decision Workspace's rule-based recommendation (EDP_22_3 D-01) consumes the package downstream. `ai` remains reserved/`null`.

**Rationale:** CFOs must be able to re-derive the decision by hand. A recommendation *embedded in* the evidence supplier blurs provenance; a separate deterministic consumer keeps evidence trustworthy. (DI-P4, DI-R2)

### D-02: Confidence is a categorical band with a measured basis
Every item carries `confidence: high|medium|low|none` **plus** `confidenceBasis` naming the measured data that produced the band (e.g. `match.overallConfidence 0.92`). No item may be `high` without a basis; absence items are always `none` with `confidenceBasis: "absence is itself the fact"`.

**Rationale:** the Phase 22.3 audit found a fabricated scalar (SEV-2). A band + basis is auditable; a scalar without a basis is not. (DI-R2)

### D-03: Sixteen fixed canonical sections with mandatory missing-evidence
`EVIDENCE_SECTION_ORDER` fixes 16 sections: identity, entity, type, status, tenant, business-context, financial-context, relationships, history, policy, risk, timeline, supporting-documents, communications, **missing-evidence**, metadata. `missing-evidence` is **always present** — as `{entityId}:no-missing` when clean, or as `missing:{id}` items with blocking gaps sorted first.

**Rationale:** consumers (workspace projection, future dashboards) need a stable layout; absence must be a first-class section, never an implicit silence. (D-07 parity)

### D-04: Assembly is deterministic and memoized per request
- Providers resolve in stable registration order; items keep provider+order; `request.now` is injectable (tests pin it).
- `EvidenceAssemblyContext.load(key, fn)` is memoized per request with in-flight deduplication — two providers needing the same record get one fetch (AuditProvider + TimelineProvider share `loadAudit`).
- `contentHash` (sha256 over section/item ids + missing + decisionReady) gives a tamper-evident integrity digest.

**Rationale:** determinism is a trust requirement for financial tooling; memoization prevents N+1 fetch patterns the same request would otherwise cause. (Law 6, 15)

### D-05: The package never rejects — provider failure degrades into typed missing
`assemble()` runs providers via `Promise.all` with a per-provider try/catch. A throwing provider contributes a `{provider}:failure` item (metadata section, status `negative`) and its `required` entries become `missing` (blocking ones flip `decisionReady` off).

**Rationale:** one bad data source must not fail an assembly the CFO is staring at — the absence of that evidence is itself the fact that matters. (Fail-open documentation principle, Phase 26.2 C-04 exception discipline)

### D-06: Required evidence with exact-id or wildcard satisfaction
`RequiredEvidence.satisfiedBy` accepts exact ids or `"doc:*"` prefixes. `isSatisfied` (assembler.ts:438) checks emitted ids against each candidate. Providers declare what a safe decision *requires*; unfilled requireds become `MissingEvidence` with `impact: blocking|advisory` and `canProceed`.

**Rationale:** explicit, testable requirements are the engine's contract with each domain — `decisionReady` is only as trustworthy as the requirements declarations.

### D-07: Providers are thin adapters — zero domain-logic duplication
The 11 AP providers read through canonical repositories (`src/server/procurement/ap-repositories/`), reuse `decision-workspace/format.ts` (`formatCurrency`, `formatPercent`, `formatCompact`, `formatNumber`), work-queue constants (`HIGH_VALUE_THRESHOLD`), `recommendation.ts` (`bandFromScore`), and `EVIDENCE_LOAD_KEYS`. No status maps, no money math, no re-formatting lives in a provider.

**Rationale:** Phase 19.0/20.0 documented the drift cost of duplicated financial logic. Providers convert repository records → evidence items only.

### D-08: Consumers receive a projection, not a bespoke builder
`buildEvidencePackage(input): Promise<EvidenceGroup[]>` is **retained** but rewritten as a thin async adapter: register AP providers → seed the request with the workspace's pre-loaded data (all 14 `EVIDENCE_LOAD_KEYS`) → `assembleEvidenceFor({ entityType: "ap.invoice", ... })` → project canonical sections into the 14-group layout by `groupId`. Engine items carry `order` (the workspace type does not), so the adapter sorts before projecting; engine-only groups (`credits`, `audit`, `timeline`) are filtered.

**Rationale (vs ARCHITECTURE.md v1's "delete buildEvidencePackage"):** deleting the function would force the UI layer or service to project — spreading layout knowledge and breaking the 14-group contract across more files. Keeping the same signature means callers changed only `buildEvidencePackage(...)` → `await buildEvidencePackage(...)`, and the 14-group contract stayed green without UI edits. (Section 6 of ARCHITECTURE.md updated to match.)

### D-09: Seeding — the request carries its data
`EvidenceRequest.seed` pre-loads the context; `context.load()` returns the seed value **without** invoking the repository fallback (verified by test). The workspace already holds fully-loaded records; re-fetching through repositories would double I/O. A consumer without pre-loaded data omits the seed and the loaders fall back to the tenant-scoped repositories.

**Rationale:** one loading path for both "workspace already fetched it" and "module asks cold" — no duplicated fetch, no new fetch contract.

### D-10: Test isolation via fresh registry instances
Engine tests construct `new EvidenceRegistry()` + `new EvidenceAssembler(registry)` per test — no global state, no AP dependency. `resetEvidenceAssembler()` exists for consumers that must re-register providers in-process. This keeps the engine testable independently of its reference providers.

## 3. Alternatives Considered

| Alternative | Decision | Why rejected |
|---|---|---|
| Delete `buildEvidencePackage`, map sections in the service | Rejected (D-08) | Spreads layout knowledge; breaks the 14-group contract surface; forces UI test churn |
| Providers compute the recommendation | Rejected (D-01) | Inverts evidence→reasoning→action; breaks hand-re-derivability |
| Numeric confidence (e.g. `0.92`) | Rejected (D-02) | Fabricated-scalar risk (SEV-2); band + basis is auditable |
| Sequential provider execution | Rejected (D-04) | Slower; per-request memoization already dedupes the fetch work |
| `Promise.allSettled` + hard-fail semantics | Rejected (D-05) | A package that rejects is unusable mid-decision; degradation into missing is the trust-preserving behavior |
| Providers reach into Prisma directly | Rejected (D-07) | Duplicates repository isolation; violates tenant-scoping pattern |
| Re-fetch PO/GRN in the adapter instead of seeding | Rejected (D-09) | Double I/O; workspace already holds the records |

## 4. Design Assumptions (to be revisited)

| # | Assumption | Watch item |
|---|---|---|
| A-1 | PO/GRN remain loaded by the workspace (no AP PO/GRN repo exists) | If a `po-grn` repository adapter ships, swap the seed for a loader without touching the surface contract (EDP_22_3 D-06) |
| A-2 | `entityType: "ap.invoice"` is the only consumer in 22.4 | Treasury/Reconciliation/Decision Intelligence register providers with their own `entityType` strings — engine path unchanged |
| A-3 | 16-section canonical layout is stable | Consumers (dashboards, reports) project from it; a section add is backward-compatible, a reorder changes `contentHash` |
| A-4 | In-memory assembly (no persistence) is acceptable for 22.4 | Long-lived cache/DB-backed evidence is a separate phase; the package is serializable |

## 5. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Provider drift duplicates domain logic over time | D-07 rule + review gate: providers convert records only; `format.ts`/constants are the shared vocabulary |
| Consumer projection diverges from engine layout | Projection is `groupId`-keyed and layout-locked by the 14-group test contract |
| Seeded data going stale while in flight | Seeds are read-only snapshots per request; freshness (`stale`) flags old timestamps in metadata |
| Global assembler cache holds stale providers across hot reloads | Lazy + idempotent; `resetEvidenceAssembler()` for tests/hot-reload |
