# Engineering Decision Packet — Phase 22.0B.5

**Date**: July 2026
**Status**: Complete
**Scope**: Enterprise Design Governance & Compliance

---

## Decision

Build automated governance tooling to enforce the Enterprise Design Language (EDL) across the entire codebase.

## Context

Phase 22.0B established the EDL token system. Phase 22.0B.1 migrated ~470+ files to EDL tokens. But without enforcement, new code could reintroduce violations. Documentation alone doesn't prevent drift.

## Options Considered

### Option A: ESLint Plugin + CI Pipeline (Chosen)

**Approach**: Custom ESLint plugin with 12 rules, CI pipeline, auto-fixer, VS Code integration.

**Pros**:
- Automated enforcement — violations blocked before merge
- Real-time feedback in VS Code
- Auto-fixer for safe violations
- Comprehensive coverage (colors, spacing, shadows, z-index, radius, typography, motion, imports)

**Cons**:
- Implementation complexity (12 ESLint rules, 5 CI scripts)
- Maintenance burden (rules must evolve with EDL)
- Initial false positives may frustrate contributors

### Option B: Code Review Only

**Approach**: Document rules in DESIGN_REVIEW_CHECKLIST.md, rely on human reviewers.

**Pros**:
- Zero implementation cost
- No tooling maintenance
- Human judgment for edge cases

**Cons**:
- Inconsistent enforcement
- violations slip through
- Reviewer fatigue
- No real-time feedback

### Option C: Visual Regression Testing

**Approach**: Screenshot comparison tests for every component/page.

**Pros**:
- Catches visual regressions
- Exact pixel-perfect verification

**Cons**:
- High infrastructure cost (browser testing)
- Brittle (breaks on unrelated changes)
- Doesn't prevent violations, only detects them
- Slow CI pipeline

## Decision

**Chose Option A** because:
1. Prevention > detection — block violations before merge
2. Real-time feedback reduces fix time
3. Auto-fixer handles 80% of violations automatically
4. ESLint is already in the stack (zero new dependencies)
5. CI integration is straightforward

## Trade-offs

| Factor | Impact |
|---|---|
| Implementation time | ~2 days |
| Maintenance | Low — rules are stable |
| False positives | Minimal — exemptions configured |
| contributor experience | Positive — real-time fixes |

## Risk Mitigation

| Risk | Mitigation |
|---|---|
| False positives blocking PRs | Exemption list for config files, token definitions |
| Rule staleness | Quarterly review of rules against EDL evolution |
| Performance impact | Rules are lightweight regex, < 1s total |
| Contributor resistance | Auto-fixer makes compliance effortless |

## Success Metrics

| Metric | Target | Actual |
