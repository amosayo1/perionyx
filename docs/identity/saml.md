# SAML 2.0 — Perionyx Identity & Access Management

**Version**: 1.0 | **Last Updated**: 2026-07-12

## Overview

Perionyx supports SAML 2.0 as a Service Provider (SP) for browser-based SSO. The system can act as an SP with any standards-compliant SAML 2.0 Identity Provider (IdP) including Microsoft Entra ID, Okta, Ping Identity, OneLogin, and custom IdPs.

## Metadata Exchange

### Perionyx SP Metadata

Perionyx exposes SAML 2.0 metadata at the provider-specific endpoint. The metadata is generated by `SSOHandler.generateSAMLMetadata(providerId)`:

```xml
<?xml version="1.0"?>
<md:EntityDescriptor xmlns:md="urn:oasis:names:tc:SAML:2.0:metadata"
    entityID="https://perionyx.com/auth/saml/{providerId}">
  <md:SPSSODescriptor protocolSupportEnumeration="urn:oasis:names:tc:SAML:2.0:protocol">
    <md:AssertionConsumerService
        Binding="urn:oasis:names:tc:SAML:2.0:bindings:HTTP-POST"
        Location="https://perionyx.com/auth/saml/{providerId}/acs"
        index="1"/>
  </md:SPSSODescriptor>
</md:EntityDescriptor>
```

### IdP Metadata Import

To configure a SAML IdP, import the IdP's metadata XML:

```typescript
identityProviderManager.registerProvider({
  id: "okta_saml",
  type: "saml",
  name: "Okta SAML",
  status: "active",
  metadataUrl: "https://okta.example.com/app/metadata.xml",
  issuerUrl: "http://www.okta.com/{org_id}",
  certificate: "-----BEGIN CERTIFICATE-----\nMII...\n-----END CERTIFICATE-----",
  attributeMapping: { /* ... */ },
  allowedDomains: ["perionyx.com"],
  autoProvision: true,
  defaultRoles: ["read_only_executive"],
  enabled: true,
  companyId: "company_456",
})
```

## Assertion Consumption

### ACS Endpoint

```
POST /auth/saml/{providerId}/acs
Content-Type: application/x-www-form-urlencoded
Body: SAMLResponse=<base64-encoded-SAML-response>&RelayState=<optional>
```

### SAML Response Processing

`SSOHandler.handleSAMLResponse()` processes the inbound SAML response:

```
Step 1: Receive base64-encoded SAMLResponse
Step 2: Decode and decompress (if deflated)
Step 3: Parse XML:
        - Extract <saml2:NameID> for user identity
        - Extract <saml2:Issuer> for IdP validation
        - Extract <saml2:AttributeStatement> for attributes
Step 4: Validate signature (if signed)
Step 5: Validate conditions:
        - NotBefore/NotOnOrAfter time window
        - Audience restriction
        - Recipient matches ACS URL
Step 6: Map attributes via provider's attributeMapping
Step 7: Resolve or provision user
Step 8: Create authenticated session
```

### XML Parsing

The SAML response parser extracts key fields:

```typescript
private parseSAMLResponse(response: string): Record<string, string> {
  const result: Record<string, string> = {}
  const nameIdMatch = response.match(/<saml2:NameID[^>]*>([^<]+)<\/saml2:NameID>/)
  if (nameIdMatch) result.NameID = nameIdMatch[1]
  const issuerMatch = response.match(/<saml2:Issuer[^>]*>([^<]+)<\/saml2:Issuer>/)
  if (issuerMatch) result.Issuer = issuerMatch[1]
  return result
}
```

## Certificate Management

### Certificate Types

| Certificate | Purpose | Management |
|---|---|---|
| **IdP Signing Certificate** | Validates SAML assertion signatures | Uploaded to Perionyx provider config |
| **SP Encryption Certificate** | Encrypts SAML assertions directed to SP | Generated and shared via SP metadata |

### Certificate Rotation

1. **Add new certificate**: Update provider config with the new certificate (old one remains valid)
2. **Dual-run period**: Both old and new certificates are accepted during transition
3. **Remove old certificate**: After all IdPs have rotated, remove the old certificate
4. **Audit logging**: All certificate changes are recorded in audit logs

## Configuration Steps

### Step 1: Register Provider

```typescript
identityProviderManager.registerProvider({
  id: "saml_enterprise",
  type: "saml",
  name: "Enterprise SAML IdP",
  status: "active",
  issuerUrl: "https://idp.company.com/adfs/services/trust",
  metadataUrl: "https://idp.company.com/FederationMetadata/2007-06/FederationMetadata.xml",
  certificate: "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----",
  attributeMapping: {
    email: "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress",
    firstName: "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/givenname",
    lastName: "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/surname",
  },
  allowedDomains: ["company.com"],
  autoProvision: true,
  defaultRoles: ["read_only_executive"],
  enabled: true,
  companyId: "company_456",
})
```

### Step 2: Share SP Metadata with IdP

Provide the IdP with the Perionyx SP metadata:

```
https://perionyx.com/auth/saml/{providerId}/metadata
```

This XML includes:
- Entity ID: `https://perionyx.com/auth/saml/{providerId}`
- ACS URL: `https://perionyx.com/auth/saml/{providerId}/acs`
- Binding: HTTP-POST

### Step 3: Configure IdP

On the IdP side, configure:
- **Audience URI**: `https://perionyx.com/auth/saml/{providerId}`
- **ACS URL**: `https://perionyx.com/auth/saml/{providerId}/acs`
- **Relay State**: Optional target URL after login
- **Name ID format**: Email address (recommended) or persistent
- **Attribute statements**: Map at minimum `email`, `firstName`, `lastName`

### Step 4: Test and Verify

1. Initiate SP-initiated SSO from Perionyx login page
2. Verify successful redirect to IdP
3. Authenticate at IdP
4. Verify callback to ACS URL
5. Confirm user is authenticated in Perionyx
6. Check audit logs for `login.success` event with `identityProvider` set

| Name ID format | `EmailAddress` |

## SSO Logout

SAML Single Logout (SLO) support is available via:

1. **SP-initiated logout**: User logs out of Perionyx → SLO request sent to IdP
2. **IdP-initiated logout**: User logs out of IdP → LogoutRequest sent to Perionyx SLO endpoint
3. **Local-only logout**: User session revoked in Perionyx only (no IdP notification)
